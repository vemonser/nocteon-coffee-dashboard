# ORDERS_SEED_PROPOSAL.md — a coherent 60 days of orders

**Status: PROPOSAL. Nothing in this file has been executed.** No migration was
written, no row was inserted, no table was touched. The proposal is here for
the decision; the numbers it describes are the numbers the checks in
`evidence/orders/results.json` could not be verified against the current
data.

---

## 1. Why the current data cannot answer the questions

The 17 seeded orders (backend migration `V107__seed_orders_reviews_contacts.sql`)
cannot support the checks this ticket asks for, for four reasons:

| Defect | Evidence |
|---|---|
| The stored total disagrees with the order's own items | **17 of 17 orders.** `ORD-2026-000001` stores 120.50 while its items are 1,825.00 + 50.00 shipping. See `evidence/orders/measurements.json` → `totals.affectedOrders` |
| The order numbers are hand-written, not generated | The seed writes `ORD-2026-000001` … `ORD-2026-000017` by hand, while the runtime generator produces `ORD-<year>-<6-digit sequence>` from the `order_number_seq` sequence. A second order inserted by the application would COLLIDE with a seeded number |
| Every order was created at the same instant | Every seeded `created_at` is `NOW()` of the migration run, so all 17 orders share one timestamp. The date-range filter, the day boundary and the "created at 23:30" checks have nothing to sort |
| 7 of 17 orders have no items at all | `ORD-2026-000006/7/9/10/12/14/15` have no `order_items` rows, so the "no items" state is 41 % of the list rather than an edge case |

There is also no history to look at: the backend has no `order_status_history`
table at all, so "a coherent status history per order" is not a data problem
today, it is a **missing table** (Phase 5, `ORDERS_CONTRACT.md`).

## 2. What is proposed

One new migration, `V1xx__seed_orders_coherent.sql`, in three parts.

### 2.1 Customers — 24 new accounts (no admins)

- 24 `users` rows, all with `role = 'CUSTOMER'`, all with a verified e-mail
  (`order.customerNN@example.test`) — never a `@aurum.local` address, so an
  admin can never be mistaken for a customer.
- 24 `addresses` rows, one per customer, with a distinct city from the
  shipping-zone table, a phone in `+20 1xx xxx xxxx` form and a street.
  The phone must be a REAL reachable number format, because the order page
  renders `tel:` and `wa.me` links from it.
- The 9 customers that already exist (ids 2–10) stay, and get 1–3 extra
  addresses each, so the list shows both a first-time and a returning
  customer.

**Why 24 and not 20:** the ticket asks for "20+ customers excluding admin
accounts". 24 gives every customer at least 3 orders over 60 days, and
leaves room for 2 of them to be created late (so the list shows customers
who joined recently).

### 2.2 Orders — 108 orders over 60 calendar days

- Spread over the last 60 days, weighted towards the recent 14 (a store that
  is growing): ~1.2 orders per day, ~2.6 per day in the last fortnight.
- The `created_at` is a real instant, never `NOW()`: 8 orders between 22:00
  and 00:30, and **at least three orders placed at 23:30 exactly** (in the
  store's time zone, Africa/Cairo) so the day-boundary behaviour is provable
  rather than assumed.
- 1–4 items per order, drawn from the real `product_variants` rows. The
  `unit_price` on each line is the variant's price **as of the order's
  date** (the current price for recent orders, the price before the last
  price change for older ones) — the price on the line is what the customer
  paid, and it is stored on the line, so a later price change does not
  rewrite history.
- `order_number` is generated by the SAME sequence the application uses
  (`nextval('order_number_seq')` → `ORD-2026-000018` … `ORD-2026-000125`),
  never written by hand. The seed therefore cannot collide with an order the
  application creates later.

| Payment status | Count | Notes |

Payment methods: ~62 `ONLINE`, ~46 `CASH_ON_DELIVERY` (COD orders are

| **A cancelled order with a reason** | `ORD-2026-000097` and 13 more | `status = CANCELLED`, `cancellation_reason` set ("Customer changed their mind", "The customer was unreachable", "Duplicate order", "The item was out of stock"), a `cancelled_at`, and a `notes` line. ### 2.5 The history — only if the Phase 5 table exists

The status history needs `order_status_history`
(`order_id`, `from_status`, `to_status`, `note`, `changed_by`,
`notify_customer`, `created_at`) — a table that does not exist yet. The
proposal therefore has two shapes:

- **If the Phase 5 migration has landed**, the seed writes one history row
  per transition, in the same transaction as the order row, so every order's
  history is consistent with its final status by construction.
- **If it has not**, the seed writes the orders and the history table is
  back-filled afterwards, from the order's own dates. The `created_at` of
  each history row is then derived, not observed — and the seed says so in a
  comment, because a fabricated history that claims to be observed is worse
  than no history.

### 2.6 The totals — the rule the seed must satisfy

For every order:

```
subtotal  = Σ line.totalPrice                    (line.totalPrice = line.unitPrice × line.quantity)
total     = subtotal − discount_amount + shipping_cost
```

and the row in `orders.total_amount` is that number, computed in the INSERT
itself (a `SELECT` over the inserted lines), never typed in by hand.

The proposal's acceptance for the seed is a single query that must return
zero rows:

```sql
SELECT o.id, o.order_number, o.total_amount,
       (o.total_amount - (SUM(oi.total_price) - o.discount_amount + o.shipping_cost)) AS delta
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id
HAVING ABS(delta) > 0.001;
```

## 3. The migration, in outline

```sql
-- V1xx__seed_orders_coherent.sql
-- 1. the customers (24) and their addresses
-- 2. the orders, one INSERT ... SELECT per order so that total_amount is
--    DERIVED from the lines in the same statement
-- 3. the order items, with unit_price = the variant's price on that date
-- 4. the refunds (2 orders) and the cancellation reasons (14 orders)
-- 5. the status history (only when the table exists)
```

The orders are inserted as `INSERT INTO orders (...) SELECT ... FROM (VALUES ...) AS v(...)` so that `total_amount` is a sub-select over the same VALUES list — one source of truth, and the check in §2.6 cannot drift.

## 4. What the seed makes verifiable — and what stays unverifiable

With this seed, these checks become provable:

- the totals card on the order page always agrees with the items (0 mismatches);
- the date-range filter (today / 7 days / 30 days) has rows on both sides of
  every boundary, and the 23:30 orders land on the day a reader expects;
- the status tabs and the cards have non-zero counts for every status;
- the cancelled branch of the progress tracker has a reason to show;
- the refunded order has a net paid that is not zero;
- the COD order can be confirmed, and its payment status can go from PENDING
  to PAID.

These stay unverifiable **without** the seed, and are reported as such in
`evidence/orders/results.json`:

| Check | Why it cannot be verified now |
|---|---|
| "the totals card agrees with the items" | 17 of 17 orders disagree; there is no order to agree |
| "the date-range filter narrows the list" | every order shares one timestamp, so today / 7d / 30d all return the same 17 |
| "a status tab with a non-zero count for every status" | `PENDING` has 0 orders; the other statuses have 1 |
| "the 23:30 order belongs to that day" | there is no 23:30 order |
| "a cancelled order shows its reason" | the backend has no `cancellation_reason` column at all |
| "net paid after a refund" | the backend records no refund AMOUNT, only the `REFUNDED` flag |
| "the status history is coherent" | the `order_status_history` table does not exist |

## 5. What the seed does NOT fix

- **The 17 existing orders keep their broken totals.** The proposal adds
  data; it does not rewrite history. Repairing them means a separate
  migration that recomputes `orders.total_amount` from their own
  `order_items` rows — which is a data repair, not a seed, and needs its own
  decision (the recorded totals are what the store "believes" it charged;
  overwriting them changes the books, not just the display).
- **The order-number collision stays.** The seed proposes generating the
  numbers from the sequence, but the 17 EXISTING seeded numbers are still
  hand-written. A migration that renumbers them is needed before the
  sequence can be trusted end to end.
- **The missing backend tables stay missing.** `order_status_history`,
  `order_notes`, the shipment fields, the refund amounts and the transaction
  reference are all in `ORDERS_CONTRACT.md` (Phase 5). The seed cannot
  invent them.
